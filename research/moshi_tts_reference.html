02 Architecture Components
BACKBONE — TEMPORAL TRANSFORMER
The main 1B-parameter Transformer that processes the text token stream and generates the first codebook of audio tokens (semantic layer). Runs at 12.5 Hz. Text tokens are shifted 1.28 seconds ahead of audio tokens — the model sees upcoming text before it needs to speak it.
1B params 12.5 Hz decoder-only causal attention
DEPTH TRANSFORMER
A 600M-parameter small Transformer that fills in codebooks 2–32 given the semantic token from codebook 1. Uses partial weight sharing (same design as Kyutai's Hibiki model) to keep parameters efficient while maintaining quality across all 32 audio codebook levels.
600M params codebooks 2–32 weight sharing
MIMI CODEC — AUDIO TOKENIZER
The same neural audio codec used inside Moshi. Encodes 24kHz audio at 1.1 kbps using Residual Vector Quantization (RVQ) into 32 codebooks at 12.5 frames/sec. Codebook 1 carries semantic phoneme information (distilled from WavLM). The TTS generates Mimi tokens; Mimi's decoder converts them to waveform.
24 kHz 1.1 kbps RVQ × 32 WavLM distilled
DSM — DELAYED STREAMS MODELING
The core technique. Text and audio run as two parallel time-aligned streams with a fixed delay between them. By making text ahead of audio, the model predicts upcoming words before synthesising their sound — giving natural prosody without waiting for the full sentence. Switching the delay direction gives an ASR model instead.
16-step delay streaming bidirectional flip
PAD TOKEN SYSTEM
Special pad tokens inserted between word tokens to control speaking rate and prosody. More consecutive pad tokens = longer pause or slower articulation. This gives fine-grained timing control without explicit duration annotations, allowing natural pauses between words and emphasis patterns to emerge from training.
implicit timing no forced align word timestamps
VOICE CONDITIONING — ZERO-SHOT CLONING
A voice embedding is extracted from a reference audio clip (as short as 10 seconds) using a speaker encoder. This embedding is prepended to the input sequence to condition the model on the desired speaker's timbre, rhythm, and prosody. For Moshi's 20K-hour synthetic dataset: Moshi's stream always received the same single voice actor's embedding (70+ speaking styles recorded as reference clips). User's stream received a randomly sampled voice embedding for each conversation, giving diversity across the training corpus.
10-sec reference zero-shot 70+ styles (Moshi) random voices (user) Wespeaker encoder
DSM Token Stream Layout — How text precedes audio at inference time
Text stream →
My name is Mo- shi and I was built by Kyu- tai
↑ runs ahead
Audio stream →
pad pad pad [mʌɪ] [neɪm] [ɪz] [moʊ] [ʃi] [ænd] [aɪ] [wɒz] [bɪlt]
↓ lags 1.28s
Pad tokens fill the initial delay window. Audio generation starts 220ms after first text token arrives. Traditional TTS would wait for the full sentence — DSM starts in under a quarter second.
03 Training Phases — Step by Step
Phase 1 Pre-training — Learning Speech from 2.5M Hours Largest stage ▶
Dataset
2.5 million hours of publicly available audio (English + French)
Transcripts
Synthetic — auto-generated by whisper-timestamped with Whisper-medium
Compute
32 × H100 Nvidia GPUs
750,000 updates, batch size 64
Audio segment length
150-second extracts (random crops from longer recordings)
Optimiser
AdamW with cosine LR schedule and linear warmup
Objective
Next-token prediction on interleaved text + Mimi audio token streams
The model is trained on a massive pool of English and French speech — podcasts, audiobooks, radio, lectures, news. Because no ground-truth transcripts exist for this data, Kyutai ran Whisper-medium with whisper-timestamped on all 2.5M hours to generate word-level aligned pseudo-transcripts. The model learns the statistical relationship between text tokens and Mimi audio tokens at every position — essentially learning what spoken language sounds like at the token level. No speaker labels, no emotion labels, no style labels are needed at this stage. This stage is shared with Moshi's own pre-training — the TTS and the dialogue model train together before diverging.
Phase 2 Fine-tuning — Real Conversational Speech (170 Hours) Quality anchor ▶
Dataset
170 hours of natural + scripted conversations, recorded by Kyutai
Format
Stereo WAV — separate channel per speaker. Ground-truth transcripts with timestamps.
Speakers
Multiple participant pairs. Diverse speaking styles, natural overlaps, backchannels.
Text delay
2-second offset between audio and text streams (vs. 1.28s at inference)
Why 2 seconds?
Lookahead at fine-tune time exceeds inference delay — ensures model learns full sentence prosody
Key outcome
TTS learns to generate two simultaneous speakers with natural dialogue timing
This is the stage that transforms a single-speaker TTS into a multi-stream streaming TTS capable of generating both sides of a conversation simultaneously. The 170-hour Kyutai-collected dataset is the only real human conversation data the TTS ever sees directly. It teaches the model how two speakers interact acoustically — how Moshi's voice and the user's voice can coexist in the same stereo file with natural timing, pauses, and turn-taking dynamics. Critically, Moshi itself is never trained on this 170-hour dataset — it is used exclusively to train this TTS model, which then generates the synthetic data that trains Moshi.
Phase 3 CFG Distillation — Improving Voice Conditioning Quality Post-training ▶
Technique
Classifier-Free Guidance (CFG) distillation
Compute
8 × H100 GPUs
Purpose
Improve speaker similarity between reference voice and generated speech
CFG distillation trains the model to more strongly condition its output on the provided voice embedding. Without this stage, the model sometimes drifts away from the reference voice during long generation. Distillation compresses the guidance signal directly into the model weights, improving voice consistency without increasing inference cost. This stage was done on only 8 GPUs — much cheaper than pre-training — and produced the final speaker similarity score of 77%+.
Phase 4 Synthesis Operation — Generating the 20,000+ Hour Dataset Production use ▶
Script source
Helium LLM (fine-tuned on Open Hermes + real conversation transcripts)
Output volume
20,000+ hours of stereo synthetic dialogue audio
Conversations
~300,000 individual dialogue files at 3–5 minutes each
Moshi voice
Fixed — single actor, 70+ styles listed in Table 19 of Moshi paper
User voice
Random — different voice embedding per conversation
Augmentation
Noise, echo, reverb applied to user stream only — Moshi stream stays clean
Content types
General knowledge, self-knowledge (Moshi/Kyutai), voice style instructions, misspellings, math, safety
Output format
Stereo WAV 24kHz + JSON transcript with word-level timestamps
Channel layout
Left = Moshi (agent). Right = User. Same format moshi-finetune expects.
This is the TTS model's primary purpose — acting as a factory. Helium generates text dialogue scripts; the TTS renders both sides as audio simultaneously. The left channel always uses the voice actor's embedding, ensuring Moshi learns a single consistent voice identity. The right channel uses a random voice each time, making Moshi robust to diverse user accents and microphone conditions. Running 100+ parallel synthesis jobs on GPUs, this factory produces the entire 20,000-hour dataset in a matter of days — the same volume would take hundreds of years of human recording.

Why no commercial TTS could have been used for Moshi: All commercial TTS systems generate one speaker at a time and produce WAV files in their own proprietary formats. Moshi's training pipeline requires stereo Mimi-encoded token sequences — both speakers simultaneously, in the exact codec format Moshi reads. Only a custom-built TTS using Mimi as its native codec could produce training data directly compatible with Moshi's architecture.
