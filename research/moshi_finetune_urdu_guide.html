What the moshi-finetune repo actually does
The honest answer before anything else
Critical fact from Kyutai's own FAQ: "Moshi only speaks English. This would require fine-tuning, which is not currently supported." — The official repo is designed for English personality/domain adaptation, NOT language switching. Using it for Urdu requires extra steps not covered by the official README.
What the official repo does
The repo fine-tunes only Helium — the 7B language model brain. Mimi (the codec) is never touched. It provides two modes: LoRA adaptation (train only small adapter matrices, ~1% of parameters) and full fine-tuning (train all 7B parameters). The training data format is stereo WAV files where left channel = Moshi speaking, right channel = user speaking.
What it CAN do
— Change Moshi's personality/tone in English
— Fine-tune on a specific domain (medical, customer service)
— Adapt to a specific speaker's conversational style
— Works on 1 H100 GPU in LoRA mode
— Full pipeline: stereo audio → auto-transcription → training
What it CANNOT do out of the box
— Teach Moshi to speak Urdu natively
— Handle Urdu Nastaliq script in inner monologue
— Fix Mimi's limited Urdu phoneme knowledge
— Change the text tokenizer (Helium uses English SentencePiece)
— Change the codec's language-specific quality

Exactly which components get updated — and which stay frozen
Component breakdown during fine-tuning
ComponentFine-tuned?WhyImpact on Urdu
Mimi encoder
CNN + RVQ quantizer		 Never. Always frozen. Codec must stay stable — changing it would break all token IDs Helium learned Mimi can physically encode Urdu audio (it's a signal-level codec). But its semantic codebook-1 tokens were distilled from WavLM on English — they may not carry strong Urdu phoneme meaning.
Mimi decoder
CNN waveform generator		 Never. Always frozen. Same reason — codec stays fixed Mimi's decoder can reconstruct Urdu audio since it's waveform-level. Quality will be acceptable but not optimized for Urdu phonemes like ص, ض, ط, ظ.
Helium LLM
7B transformer, all layers		 YES — this is the entire point LoRA adapters trained on all linear layers, OR full fine-tune of all 7B params This is where Urdu language behavior is learned. Helium must learn: Urdu word sequences, Urdu grammar, Urdu conversational patterns from the dialogue data.
Text tokenizer vocabulary
SentencePiece model		 NOT in official repo
YES in nu-dialogue fork		 Official repo assumes English tokenizer. nu-dialogue fork lets you swap in any SentencePiece model. This is the most critical piece for Urdu. Without an Urdu-capable tokenizer, inner monologue text tokens will be garbage — the model cannot think in Urdu.
Text embedding table
maps token IDs → vectors		 Optional (lora.ft_embed) If you change the tokenizer, you must reinitialize the embedding table for new token IDs Required for Urdu Nastaliq script. The nu-dialogue fork has an --init_text_embeddings flag exactly for this.
Depth Transformer
small model for inter-codebook prediction		 Yes, trained with Helium Predicts codebooks 2–8 given codebook 1. Trained jointly. Learns Urdu acoustic patterns across codebook layers from training audio.
The biggest misconception: people think fine-tuning Moshi means "teaching it a new voice." It doesn't. Fine-tuning teaches Helium new conversational patterns and language content. The voice quality (Mimi) stays the same. For Urdu, you are teaching the brain to think and respond in Urdu — the ear and mouth (Mimi) stay as is.

The 4 specific challenges for Urdu — and how solvable each one is
1
Wrong text tokenizer — Helium uses English SentencePiece
Helium's tokenizer was built on French/English text. Urdu uses Nastaliq Arabic script (right-to-left). The tokenizer has almost no Urdu coverage — Urdu text will be tokenized as unknown characters or split into meaningless byte fragments. This means the Inner Monologue (Helium's thinking layer) cannot reason in Urdu.
Solvability: Moderate. The nu-dialogue fork solves this — you supply your own SentencePiece model trained on Urdu text and re-initialize the embedding table. Requires: an Urdu SentencePiece vocab (you can train one from Common Crawl Urdu text in ~30 minutes), and reinitializing the embedding layer before fine-tuning.
2
Mimi's semantic tokens — distilled from English-dominant WavLM
Mimi's codebook-1 (semantic) tokens were distilled from WavLM, which was pre-trained primarily on English speech. Urdu phonemes like retroflex consonants (ٹ, ڈ, ڑ), aspirated stops (پھ, بھ), and the schwa vowel may not map to distinct cluster IDs. Different Urdu sounds could collapse to the same token.
Solvability: Acceptable for now. Mimi is still a signal-level codec — it can encode and reconstruct Urdu audio acoustically even if semantic tokens are not perfect. Helium will learn to work with the available token vocabulary. The output will be intelligible Urdu but may lose some subtle phoneme distinctions. Full fix requires fine-tuning Mimi with an Urdu-capable SSL model, which is a separate research project.
3
Limited Urdu dialogue data — Moshi needs stereo 2-speaker conversational audio
The official repo requires stereo WAV files with both speakers on separate channels — one entire conversation per file. Urdu has limited publicly available conversational dialogue datasets in this exact format. Most Urdu speech data is read-speech (people reading text), not natural dialogue.
Solvability: Manageable with synthetic data. You can synthesize stereo dialogue from text Q&A pairs using a Urdu TTS system. Use any Urdu TTS (Google Cloud, Microsoft Azure, or open-source Urdu TTS) to generate both sides of the conversation, mix into stereo, and use that as training data.
4
Helium has very limited Urdu world knowledge
Helium was pre-trained primarily on French and English text. Its knowledge of Urdu topics, vocabulary, grammar, and cultural context is minimal.
Solvability: Fine-tuning directly addresses this. Training Helium on Urdu conversational data teaches it Urdu language patterns. You can supplement with Urdu text-only training (just text tokens, no audio required) before the audio fine-tuning step — this is much cheaper.

Complete step-by-step plan to build Urdu Moshi
1
Use the nu-dialogue fork, not the official repo
The community fork (github.com/nu-dialogue/moshi-finetune) supports custom text tokenizers, which is essential for Urdu Nastaliq script. It was used to build J-Moshi (Japanese) using the exact same steps you need for Urdu.
git clone https://github.com/nu-dialogue/moshi-finetune cd moshi-finetune && pip install -e .
2
Train an Urdu SentencePiece tokenizer
Train a new tokenizer on Urdu text so the inner monologue can think in Urdu. Use the same vocabulary size as Helium's original tokenizer (check config.json — typically 32,000 or 48,000). Use Common Crawl Urdu, Wikipedia Urdu, and any Urdu text corpus.
import sentencepiece as spm spm.SentencePieceTrainer.train( input="urdu_corpus.txt", model_prefix="urdu_spm", vocab_size=32000, # must match Helium's vocab size character_coverage=0.9995, # high coverage for Urdu script model_type="bpe", pad_id=0, unk_id=1, bos_id=2, eos_id=3 )
3
Initialize the model for Urdu fine-tuning
Use the nu-dialogue init script to reinitialize text embeddings for the new tokenizer vocabulary, and add the user-stream prediction modules.
python -m tools.init_moshi_for_ft \ --moshi_lm_repo kyutai/moshiko-pytorch-bf16 \ --save_dir init_models/moshiko-urdu \ --model_dtype bfloat16 \ --extend_modules_for_user_stream \ --init_text_embeddings \ ← reinitialize for Urdu tokenizer --text_tokenizer_repo ./urdu_spm.model
4
Prepare stereo Urdu dialogue dataset
Generate synthetic dialogues using Urdu TTS or record natural conversations. Mix to stereo: left = assistant voice, right = user voice. Transcribe with Whisper (language=ur) to get timestamps.
# Synthesize stereo dialogue from text Q&A pairs # Left channel: TTS with "Urdu Female Voice A" # Right channel: TTS with "Urdu Male Voice B" # Then transcribe with Whisper for timestamps: whisper conv_001.wav --language ur --output_format json # Run annotate script for all files: python -m tools.tokenize_audio \ --audio_dir ./urdu_audio \ --output_dir ./urdu_tokens \ --text_tokenizer_repo ./urdu_spm.model \ --no_whitespace_before_word # Urdu has no spaces between some words
5
Run LoRA fine-tuning
Start with LoRA (rank 128) for speed. If results are poor after 2,000 steps, switch to full fine-tuning. Use a lower learning rate than default since you reinitialised embeddings.
torchrun --nproc-per-node 1 -m train urdu_config.yaml # urdu_config.yaml key settings: # lora: # enable: true # rank: 128 # ft_embed: true ← full fine-tune embeddings (new tokenizer needs this) # optim: # lr: 1e-5 ← lower than default 2e-6 due to reinitialized embeddings # max_steps: 5000 ← more steps for language transfer # text_padding_weight: 0.05
6
Test and iterate
Run the Moshi web server with your fine-tuned weights. Test with Urdu speech input. Check if inner monologue produces Urdu text tokens. Iterate with more data if responses revert to English.
python -m moshi.server \ --lora-weight=./checkpoints/lora.safetensors \ --config-path=./checkpoints/config.json

The single most impactful thing you can do: Generate high-quality synthetic Urdu dialogue data before fine-tuning. 50 hours of synthetic Urdu Q&A conversations (both speakers TTS-generated) will produce a far better result than 5 hours of real recorded audio, simply because of quantity. Kyutai used 20,000 hours of synthetic data — quality of real data matters, but quantity dominates at the early stages.
